# codei18n-jetbrains 项目章程

## 核心原则

### I. JetBrains 插件开发规范

**原则**: 严格遵守 JetBrains Platform SDK 开发规范和最佳实践.

**理由**: JetBrains 插件必须符合平台规范以确保兼容性、稳定性和用户体验. 违反规范会导致插件审核失败、兼容性问题和维护困难.

**要求**:
- 必须使用 IntelliJ Platform SDK 官方推荐的 API 和模式
- 必须遵循 JetBrains Plugin Development Guidelines
- 必须通过 Plugin Verifier 验证
- 禁止使用已废弃或内部 API, 除非有明确的技术理由并记录在案
- UI 组件必须符合 IntelliJ Platform UI Guidelines
- 必须正确实现扩展点(Extension Points)和服务(Services)

### II. Java 业界规范

**原则**: 遵守 Java 编程最佳实践和行业标准.

**理由**: 保持代码质量、可维护性和团队协作效率. Java 规范确保代码的一致性和专业性.

**要求**:
- 必须遵循 Java Code Conventions 或 Google Java Style Guide
- 必须使用 Java 8+ 特性(根据 JetBrains 平台要求调整)
- 必须正确处理异常、资源管理和并发
- 必须使用有意义的命名、清晰的注释和适当的文档
- 必须避免常见的反模式(如 God Object、过度耦合等)
- 包结构必须清晰、模块化、符合职责分离原则

### III. 单元测试覆盖率要求(不可协商)

**原则**: 单元测试覆盖率必须大于 60%.

**理由**: 高测试覆盖率是代码质量和可靠性的关键指标. 对于插件项目, 充分的测试能够: 
- 防止回归错误
- 确保跨 IDE 版本的兼容性
- 简化重构和维护
- 提供代码使用示例和文档

**要求**:
- 每个新功能必须包含单元测试, 覆盖率不低于 60%
- 关键业务逻辑和复杂算法必须达到更高覆盖率(建议 80%+)
- 测试必须使用 JUnit 5 或 JetBrains 推荐的测试框架
- 测试必须独立、可重复、快速执行
- 必须包含正常场景、边界条件和异常场景的测试
- 禁止为达到覆盖率而编写无意义的测试

### IV. codei18n CLI 封装原则

**原则**: 正确封装和集成 Go 开发的 codei18n 命令行工具.

**理由**: 插件的核心功能依赖于 codei18n CLI 工具. 封装必须稳定、高效、用户友好.

**要求**:
- 必须使用进程管理正确调用 codei18n 可执行文件
- 必须处理所有可能的错误场景(工具缺失、版本不兼容、执行失败等)
- 必须提供清晰的错误消息和用户指导
- 必须支持 codei18n 的所有核心功能
- 必须实现进度反馈和可中断的长时间操作
- 必须验证 codei18n 版本兼容性
- 输入/输出必须正确编码处理(支持多语言字符)

### V. 用户体验优先

**原则**: 插件必须提供流畅、直观、符合 IDE 用户习惯的体验.

**理由**: 用户体验直接影响插件的采用率和用户满意度. IDE 插件必须无缝集成到开发工作流程中.

**要求**:
- 操作必须响应迅速, 长时间操作必须显示进度
- 必须提供撤销/重做支持(如适用)
- 必须使用 IDE 原生 UI 组件和交互模式
- 必须提供快捷键支持
- 必须提供清晰的配置界面和帮助文档
- 错误消息必须用户友好、可操作
- 必须支持 IDE 的主题系统

### VI. 向后兼容性

**原则**: 插件必须支持合理范围的 IDE 版本, 并妥善处理版本差异.

**理由**: 用户使用不同版本的 IDE, 插件应尽可能覆盖主流版本.

**要求**:
- 必须明确声明支持的 IDE 版本范围
- 必须测试最低和最高支持版本
- API 使用必须考虑版本兼容性
- 版本特定代码必须清晰标注和隔离
- 升级必须提供迁移路径和说明

### VII. 可观测性与调试

**原则**: 插件必须提供充分的日志和诊断信息.

**理由**: 插件问题诊断往往困难, 充分的日志对于支持和维护至关重要.

**要求**:
- 必须使用 IntelliJ Platform 的日志框架
- 必须记录关键操作、错误和警告
- 日志级别必须合理设置(DEBUG、INFO、WARN、ERROR)
- 不得记录敏感信息(用户数据、密钥等)
- 必须提供诊断信息收集机制(如适用)

## 技术约束

### 技术栈
- **语言**: Java 8+
- **构建工具**: Gradle (推荐使用 Gradle Plugin for IntelliJ Platform)
- **测试框架**: JUnit 5, Mockito
- **IDE 平台**: IntelliJ IDEA 2020.3+ (根据目标用户调整)
- **外部依赖**: codei18n CLI (Go 实现)

### 性能要求
- UI 操作响应时间 < 100ms(不包括 codei18n 执行时间)
- codei18n 长时间操作必须异步执行, 不阻塞 UI 线程
- 内存使用必须合理, 避免内存泄漏
- 启动时间必须最小化(延迟加载, 按需初始化)

### 安全要求
- 必须安全处理用户输入(防止命令注入)
- 必须验证 codei18n 可执行文件完整性(如适用)
- 不得存储敏感信息在明文中
- 必须遵循 JetBrains 安全最佳实践

## 开发工作流程

### 代码审查要求
- 所有代码必须经过审查才能合并
- 审查必须验证: 
  - 符合 Java 和 JetBrains 规范
  - 测试覆盖率达标
  - 无明显性能或安全问题
  - 代码清晰、可维护

### 测试门禁
- 所有单元测试必须通过
- 测试覆盖率必须 ≥ 60%
- 必须通过 Plugin Verifier 验证
- 必须通过静态代码分析(如 IntelliJ IDEA Inspections)

### 提交规范
- 提交消息必须清晰描述变更内容
- 建议使用约定式提交(Conventional Commits)格式
- 每次提交必须是原子性的、可编译的

### 发布流程
- 必须更新版本号(遵循语义化版本)
- 必须更新 CHANGELOG
- 必须测试发布包
- 必须提供发布说明

## 治理

### 章程修正
- 章程修正需要: 
  1. 提出修正提案并说明理由
  2. 团队审查和讨论
  3. 更新受影响的模板和文档
  4. 更新版本号和修正日期

### 复杂性证明
- 如需违反简单性原则(如引入复杂架构或依赖), 必须: 
  1. 记录在实施计划的"复杂度跟踪"部分
  2. 解释为什么需要
  3. 说明为什么更简单的方案不可行
  4. 获得审查批准

### 合规性验证
- 每个 PR 必须验证是否符合章程要求
- 定期审查代码库是否符合章程原则
- 测试覆盖率必须在 CI/CD 中自动检查

### 运行时指导
- 开发过程中参考 `.specify/templates/` 中的模板
- 使用 `/speckit.*` 命令辅助开发流程
- 遇到章程冲突或不确定时, 优先咨询团队
